# /e2e-mock — Mock 파이프라인 E2E 완주 검증

목적: 데모 시나리오가 살아있는지 **무대 전에** 안다. chrome-devtools MCP로 정본 대본을 자동 주행하고 단계별 소요를 표로 보고. Mock 경로라 키·과금 0.

정본 대본: `docs/finals/evidence/mock-overhaul/README.md` (2026-07-03 개편). 아래 표는 그 실행 버전 — 대본이 바뀌면 이 표도 갱신할 것. 2026-07-05 라이브 완주로 전 단계 검증됨.

## 대상

- **라이브(기본)**: `https://jb-marker.vercel.app/cockpit` — 먼저 HF `/health` 확인. ⚠️ 라이브는 로컬보다 3~4배 느림(아래 실측).
- **로컬**: `http://localhost:3100` (백엔드 8151 선행 기동. 백엔드 재기동 시 run 소멸 — 데모 당일 서버 먼저 띄우고 run 준비).

| 항목 | 값 |
|---|---|
| Mock(데모) 모드 | ON (기본 ON) |
| Marker 엔타이틀먼트 | **Pro로 토글** (기본 Free — 안 하면 Review가 심의를 안 돌림) |

## 주행 규칙 (CDP)

- `take_snapshot` → 화면 텍스트로 uid 찾기 → `click`/`fill`. 스크린샷 말고 스냅샷.
- 클릭 직후 다음 단계의 기대 텍스트로 `wait_for`. **wait_for 텍스트 선정 규칙**:
  - 이미 화면에 있는 텍스트(내가 보낸 메시지·가이드 배너·과거 챗)와 겹치면 즉시 오탐 — 새 응답에만 나올 고유 문구로.
  - `critical 0`처럼 DOM 노드가 쪼개진 텍스트는 매칭 실패 — 판정 배지(`BLOCKED`/`WARN`/`PASS`) 또는 버튼 라벨(`경고 확인 후 진행`) 같은 단일 노드 텍스트로.
  - "확정 & 다음 →" 버튼은 처리 중 `처리 중…`으로 바뀜 — 재활성화 대기는 `확정 & 다음`으로.
  - 챗 응답 완료는 `생성 중` 소멸을 evaluate_script 폴링으로 확인하는 게 가장 확실.
- 재검토·비주얼 베이크는 라이브에서 60~200초 — timeout 300초로.
- 단계 경계마다 `evaluate_script`로 `Date.now()` 기록 → 최종 타이밍 표.

## 함정 (하나라도 어기면 시나리오가 멈춤)

1. **챗 모델 셀렉터는 뷰 전환마다 "Claude"로 리셋** — 챗 입력 전 매번 "Marker Pro" 재선택.
2. 수정 지시는 `리뷰 결과대로 카피 교정해줘` — **"수정"은 시그널 미발동**, 반드시 "교정".
3. **Review 진입 시마다 ko main.scene 에디터가 자동으로 열림** — "검토 시작"/"재검토" 전에 반드시 **"파일 닫기"**.
4. 티키타카(#6) 수행 시 재검토는 PASS가 아닌 **WARN — critical 0 + warning 1**(고지 비율) — "경고 확인 후 진행"이 정상. 티키타카 생략 시 warning 0.
5. `design/final/*/main.scene`은 Design 4회차 확정 후에는 **없다**(metadata.md만 생성). 5회차(완료) + Review 진입 시점에 트리에 등장 — 중간에 없다고 FAIL 처리 금지.
