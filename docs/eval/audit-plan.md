# D2 — jb-marker 기능 Audit & Critique 계획서

> 목적: D3(자가 점검)이 **근거 기반**으로 채점되도록, 무엇을 어떤 깊이로 감사하고
> 어떤 증거를 어떻게 수집할지 사전 정의한다. critique는 "잘됨" 나열이 아니라
> 감점 요인·갭·리스크를 적극 발굴하는 비판적 검토를 지향한다.

## 1. 감사 원칙

1. **자체보고 불신**: "구현됨"이라는 README/주석/커밋 메시지를 액면 신뢰하지 않는다.
   주장은 반드시 1차 증거(코드·테스트·실행)로 재확인한다.
2. **증거 등급제**: 모든 판정에 아래 등급을 표기한다.
   - **A. 코드 인용** — `file:line` 직접 인용으로 로직 확인.
   - **B. 자동 테스트** — 통과하는 테스트가 동작을 보증.
   - **C. 로컬 실행** — 로컬에서 실제 호출해 산출물 확인.
   - **D. 라이브 E2E** — 배포 환경에서 실제 사용자 흐름 확인.
3. **정합성 우선**: 평가 4.1(제안서↔명세서↔실제 일관성)은 감점 핵심. 문서가 코드보다
   과장된 지점을 적극 찾는다(환각·overclaim 탐지).
4. **준법 정확성 보수적 판정**: 법령 매핑은 "그럴듯함"이 아니라 조문·근거 데이터 존재로 판정.

## 3. 증거 수집 방법

### 3.1 정적 (등급 A·B)
- 각 하네스의 LLM/이미지/비전 호출 지점, 산출 VFS 경로, grounding 부착 로직을 코드 인용으로 확인.
- 규칙엔진: policies yaml 조문 ↔ rules_engine 판정 로직 대응 확인.
- 테스트 실행: `cd backend && pytest`(전체 통과 수), `cd frontend && npm run test && npm run typecheck && npm run build`.

### 3.2 동적 (등급 C — 로컬, **Mock 모드**)
- C1(Mock 토글) 구현 후, 로컬에서 4 스튜디오를 Mock으로 완주해 산출물 구조·흐름 확인(무비용).
- VFS 트리·grounding 메타·usage 기록이 실제로 생성되는지 확인.

### 3.3 라이브 (등급 D — 실 LLM, **유료**)
- D4의 풀 시나리오 E2E를 실 키로 1회 완주(D4에서 비용 산정 후 실행).
- 실제 산출물(스펙·디자인·리뷰·발송계획)의 품질·grounding·다국어 동등성 확인.
